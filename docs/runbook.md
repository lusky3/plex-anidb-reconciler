# Rollout runbook

State lives in `/data` (host: `/opt/plex-anidb-reconciler`): `ledger.sqlite` (applied and failed writes only, each with a `before` and `after` JSON column: the snapshot state/view date of the fid, Plex `viewCount` and Shoko's `LastWatchedAt`/`WatchedCount` read just before the write; `after` is the date written to Shoko or `{"plex_played": true}`, empty for a failed write) and one report per run at `reports/<run_id>.csv` plus a self-contained `reports/<run_id>.html` with the same rows and the summary counts on top (the newest 200 of each are kept). Ledgers from older versions get the two columns added on first open (old rows stay empty).

Secrets come from Doppler, project `misc`, config `dev`: `SHOKO_API_KEY` and `PLEX_TOKEN` (or wherever you keep the Plex token). If `PLEX_TOKEN` is not in Doppler yet, add it there next to `SHOKO_API_KEY` before step 6 (`doppler secrets set PLEX_TOKEN --project misc --config dev`). Every `docker compose` command below is prefixed with `doppler run --project misc --config dev --` so both reach the container; alternatively put them in a root-only env file and use `docker compose --env-file /root/pxar.env ...`.

- [ ] 0. **Image and host directories.** Use the published image (`ghcr.io/lusky3/plex-anidb-reconciler`); for production pin a version tag or digest in compose. After the first CI publish the GHCR package is private: either make it public (GitHub → Packages → `plex-anidb-reconciler` → Package settings → Change visibility) or run `docker login ghcr.io` on the host with a token that has `read:packages`, or `docker compose pull` will fail. It is distroless (no shell: debug with `docker run --rm --entrypoint /app/.venv/bin/python <image> -c ...`), and compose runs it with a read-only root filesystem (plus a small tmpfs `/tmp`), so all state must live in `/data`. The container runs as uid 10001. Create the state dir with that owner, or the first run fails writing `ledger.sqlite` / `reports/` (Docker would create it root-owned): `sudo install -d -o 10001 -g 10001 /opt/plex-anidb-reconciler`. The MyList dir mounted at `/mylist:ro` must be readable by uid 10001: check as that uid with `sudo -u '#10001' ls /opt/shoko/config/Shoko.CLI/MyList/mylist.json` (it must list the file without "Permission denied"; fix with world-read or a matching group).
- [ ] 1. **Backups.** Copy `/opt/shoko/config/Shoko.CLI/SQLite`; export MyList on anidb.net.
- [ ] 2. **Plex webhooks.** Plex -> Settings -> Webhooks: remove any URL pointing at Shoko (`/plex` or `/plex.json`).
- [ ] 3. **Shoko settings.**
  - `AniDb.MyList_DeleteType=1`
  - `MyList_SetUnwatched=false`
  - `MyList_ReadUnwatched=false`
  - `MyList_StorageState=4` (Remote)
  - `Import.UseExistingFileWatchedStatus=false`
  - `MyList_UpdateFrequency=1` (Never) until the backfill is done
- [ ] 4. **One MyList sync:** `GET /api/v3/Action/SyncMyList`. Expect ~7.2k state pushes (HDD -> Remote), about 12 h of paced UDP. The 23 locally watched files may see a transient +/-5 h date shift that the next sync corrects (spec section 4).
- [ ] 5. **Path map.** Plex and Shoko see the same files under different prefixes. Find Plex's prefix from any anime episode: Plex Web -> episode -> `...` -> Get Info -> the file path (or `curl -s -H "X-Plex-Token: $PLEX_TOKEN" -H 'Accept: application/json' http://plex:32400/library/metadata/<ratingKey> | jq -r '.MediaContainer.Metadata[0].Media[0].Part[0].file'`), e.g. `/data/TV/tv_anime/...`. Find Shoko's prefix for the same file: Shoko Web UI -> file details -> location, or `GET /api/v3/File/<id>?include=AbsolutePaths` (e.g. `/mnt/media/TV/tv_anime/...`). Set `PATH_MAP` to the differing leading parts, `plexprefix=shokoprefix`, `;`-separated if there are several roots (e.g. `PATH_MAP=/data/TV=/mnt/media/TV`).
- [ ] 6. **Dry run:** `doppler run --project misc --config dev -- docker compose run --rm plex-anidb-reconciler plan` (uncapped: every executable row shows `dry_run`). Review the CSV in `/data/reports/`. Before applying, check the R4 `no_shoko_match`, `ambiguous_path` and `fallback_match` counts in the stdout summary (one line per rule, status and, for reports, reason, e.g. `R4 reported no_shoko_match: 3`; writes appear as e.g. `R2 dry_run: 120`). `no_shoko_match` and `ambiguous_path` should be small (a handful of files Shoko does not know); hundreds mean `PATH_MAP` is wrong. `fallback_match` should be zero: it means a Plex path, after the `PATH_MAP` rewrite, is not exactly any Shoko `AbsolutePath` and was matched only by parent folder + filename (which can be another show's same-named episode), so the item is reported and never written. Any non-zero `fallback_match` count means `PATH_MAP` is wrong or missing a root: fix it and re-run `plan` before applying. A dry run never reads Shoko `UserStats`, so `skipped`/`shoko_already_watched` rows only appear in `apply` runs: there a planned R2/R2b for a file Shoko already has a watched date for is skipped (never overwritten), and it recurs on every run until `mylist.json` shows that fid watched.
- [ ] 7. **Canary:** `doppler run --project misc --config dev -- docker compose run --rm plex-anidb-reconciler apply --rules R2 --limit 1` (a plain `--limit 1` would only run an R1, which runs first). To pick a specific row from the dry-run CSV use `--file-id <file_id>` as well. Before the write the reconciler reads `GET /api/v3/File/<id>/UserStats`; on the targeted Shoko 5.3.3 a never-watched file answers HTTP 404 `No FileUserStats entry for the given fileID for the current user`, which counts as unwatched (any other 404 or error fails the write with no PUT). After it, verify UserStats, the Shoko log line `UpdateMyListFileStatusJob ... | True | <date>`, and the date on anidb.net. Then work through the live-verification checklist below before step 8.
  - **Accepted risk: the R2 date may come from an older file.** Plex history has no file identity. An R2 date is the Plex item's earliest owner play (or, without history, its `lastViewedAt`), credited to the Shoko file behind that item *now*. If this file replaced an older release of the episode that was played in Plex but never recorded in AniDB, that older play becomes this file's AniDB view date. This is accepted: the alternative would be never backfilling such episodes. R2b (episode already watched via another file) does not have this problem: it only counts plays after both the AniDB date and the current file's Shoko import time. Keep it in mind when checking the canary date and when reviewing R2 rows in the dry-run report.
- [ ] 8. **Backfill:** R1 first (Plex-only), then the AniDB writes: `doppler run --project misc --config dev -- docker compose run --rm plex-anidb-reconciler apply --rules R1`, then `doppler run --project misc --config dev -- docker compose run --rm plex-anidb-reconciler apply --rules R2,R2b`, each repeated in batches (every run is capped by `MAX_WRITES`, default 500) until the summary shows no `capped` rows.
- [ ] 9. **Go live.** When the Shoko queue is empty:
  - set `MyList_UpdateFrequency=4`
  - deploy `serve`: `doppler run --project misc --config dev -- docker compose up -d`
  - in Tautulli add a **Webhook** notification agent: Webhook URL `http://plex-anidb-reconciler:8787/trigger`, method `POST`, trigger "Watched", and under Data -> Watched -> JSON Data: `{"rating_key": "{rating_key}"}`. Each notification then runs a reconcile that plans everything exactly like a full run and executes (and lists in the report) only that Plex item's actions; triggers that arrive during a run are merged into one run for all their rating keys. A trigger without a usable `rating_key` (empty or non-JSON body, missing or non-numeric key) runs a full reconcile, and the periodic poll is always a full run.

## Live verification (after the canary, before the backfill)

Stop at the first item that does not hold and report it; do not continue the backfill.

- [ ] **PATH_MAP prefix.** The canary row's Plex path, rewritten by `PATH_MAP`, is exactly the Shoko `AbsolutePath` of that file id (step 5); the `plan` summary shows only a handful of `no_shoko_match`/`ambiguous_path` and no `fallback_match`.
- [ ] **No Plex webhook to Shoko.** Plex -> Settings -> Webhooks lists nothing pointing at Shoko (step 2); otherwise Plex plays reach AniDB twice.
- [ ] **Same instant everywhere.** The canary date in the CSV (`when`, UTC), the Shoko log line `UpdateMyListFileStatusJob ... | True | <date>` and the view date on anidb.net are the same instant (allowing for each one's timezone display).
- [ ] **Shoko `Created` is UTC.** `GET /api/v3/File/<id>` for the canary file returns `Created` with an offset (or `Z`). A naive value is read as `SHOKO_TZ`; if Shoko actually sends UTC without an offset, R2b import-time gating is shifted by the zone offset: stop and report.
- [ ] **Single-file re-check returns xrefs.** `GET /api/v3/File/<id>?include=XRefs,AbsolutePaths&includeXRefs=true&includeDataFrom=AniDB` for the canary file returns `SeriesIDs[].EpisodeIDs[]`, `AniDB.ID` and `Locations[].AbsolutePath` (the write is only made if the file still has the exact path the Plex item matched). If it does not, every write fails safe as `failed`/`shoko_changed` (nothing is written): stop and report.
- [ ] **Does Plex `/:/scrobble` create a history row?** Before the first R1 apply, note the owner history count for one R1 item (`curl -s -H "X-Plex-Token: $PLEX_TOKEN" -H 'Accept: application/json' 'http://plex:32400/status/sessions/history/all?accountID=1&metadataItemID=<ratingKey>' | jq '.MediaContainer.size'`), run `apply --rules R1 --limit 1`, and check again. If the count went up, stop and report: R1-marked keys already ignore `lastViewedAt`, but these history rows would also have to be excluded before R2/R2b may run.
- [ ] **Multi-episode files in mylist.json.** Pick a file you know spans several episodes (a double-episode release) and look up its `FileID` in `mylist.json`. There must be one entry per (`FileID`, `EpisodeID`). If only one `EpisodeID` per `FileID` is present, every multi-episode file will report `eid_mismatch`: it fails safe (nothing is written for it) but those files never reconcile; stop and report.

## Notes

- `pxar serve` runs an apply immediately at startup and on every container restart, so deploy it only after the backfill (step 8, go live in step 9). Fix config problems before enabling `restart: unless-stopped` loops: a crash-looping container would re-run apply on each start.
- `/trigger` has no authentication. Keep port 8787 unpublished and reachable only on the docker network.
- `GET /healthz` reports the last run, `"snapshot": "ok" | "stale" | "unavailable"` and `"loop": "ok" | "stale"`. A persistently `stale` snapshot means Shoko's daily MyList sync is not refreshing `mylist.json`: R2/R2b are deferred until it is. `"loop": "stale"` (HTTP 503) means the poll loop thread died or has not beaten within 2 x `POLL_MINUTES` + 5 min while idle. While a run is active `/healthz` reports `"run_active_since"` (UTC) and stays 200 until that run has lasted `RUN_STALE_MINUTES` (default 360); after that it is 503 with `"loop": "stale"`, meaning the run is hung: restart the container (applied writes are already in the ledger).
- The image has a Docker `HEALTHCHECK` on `/healthz` (healthy = HTTP 200). It only means something for `serve`; one-shot `plan`/`apply` containers never listen, so they may show `starting`/`unhealthy` while they run, which is harmless (`docker compose run` has no switch to disable it; with plain `docker run` add `--no-healthcheck`). The probe is `pxar healthcheck`, which derives its target from `LISTEN` (loopback for `0.0.0.0`/empty host, `::1` for `[::]`).
- Shutdown: on SIGTERM the service stops accepting triggers and tells an in-flight run to stop at its next write boundary: the write already in flight completes and is recorded, the remaining actions are listed in that run's CSV as `skipped` with detail `shutdown`, and the next run re-plans them. It waits up to `SHUTDOWN_GRACE_S` (default 25 s) for the run to end, logging a warning if it is still running; compose sets `stop_grace_period: 30s` to stay above it. If the grace is exceeded (for example a hung Shoko call) and Docker sends SIGKILL, a write cut off at that instant may not have reached the ledger. It is re-planned next run as the same file with the same date (an idempotent PUT); once the snapshot shows the fid watched, nothing is planned.
- Exit codes: `0` ok, `1` config error, `2` a write failed or the run failed. On a Shoko/Plex failure the sanitized client message is printed (method, path and HTTP status or exception type, never secrets or query strings); for any other error only the exception type is printed.
